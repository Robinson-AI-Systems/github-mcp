# PLAY-2 — Enrolled runtime hosts for Robinson's Playground

## Owner authorization 2026-10-31

Owner commissions enrolled runtime hosts: any user may enroll their own computer or server as a Playground execution host under their own connection; the owner's PC (desktop-ol64acp, tailnet device name) is instance #1. Each user brings their own compute, as each user brings their own credentials today; no user ever receives the owner's credentials, keys or machines. Commissioned into the builder brief the same date (the RTC 2 builder brief carries this card in full, with the alignment review's ten questions attached). Build after or alongside PLAY-1's live acceptance; PLAY-1 remains the repo's stated next step and is not blocked by this card.

## Commissioned outcome

1. **Enrolled allocations.** Generalize the allocation registry from operator settings to per-tenant records — {workspace_id, binding, origin} plus enforcement observations, in the PUB-1 tenant pattern — written by an enrollment flow instead of by the operator. Origin is never a tool argument: an enrolled origin becomes trusted by registration and pinning, exactly as worker origins are pinned today. The agent surface does not change (`github_playground_execute` / `read` / `cancel`); backend placement is expressed as allocation placement plus availability, not a new tool family.
2. **Device setup and pairing.** An install/pairing flow the user runs on their own machine: the worker installs the existing coding-workspace image and supervisor unchanged, pins the control plane's public key, and proves readiness with an enrollment canary execution before any real work is offered. A worker update channel is part of this card. Reachability from NAT'd home networks is via an owned outbound tunnel (the shape PLAYGROUND-OPERATIONS already names for worker hosting); the control plane accepts no caller runtime URL.
3. **Host continuity for enrolled machines.** Reuse the native-git host-continuity machinery — origin pins (current plus previous), cutover timestamps, capabilities/readiness checks before use, drain-don't-kill semantics, unknown pins refuse before credentials or requests. A user's machine going offline, sleeping, or being replaced is the tenant-scale version of the git worker's host moves. Enrolled hosts report in the existing availability vocabulary (ready / constrained / recovery / git_only).
4. **Recovery and journal, reused wholesale.** requestKey idempotent intents, uncertain-never-rerun receipts, result_store 24-hour connection-scoped handles, hash-pinned log windows, and revocation that terminates running workloads. Revoking an enrollment terminates its running work.

## Hosted fallback — open question, not decided

Users without a machine of their own need a hosted path. The owner's candidate (Vercel Sandbox) conflicts with the recorded split ("Keep Vercel for MCP, Neon for metadata and Dokploy for execution") and with HOSTING-COST-POLICY free-tier economics. The builder answers in this card's design phase: who pays for fallback compute and under whose account and quota it runs; session and time limits of the candidate sandbox against a four-hour execution; and whether the fallback is an operator Dokploy pool, a paid-tier feature, or the owner's candidate made to fit the policy. No fallback is built until that answer is recorded here.

## Known friction to evaluate in design

The sealed broker transfer is bounded at 100 MiB with no symlinks; attaching appliance-desk to an enrolled device may exceed it. Evaluate direct clone by the image's embedded native-git engine on the device against raising the broker bound; appliance-desk is the test case. Device attachment is not promised until this is answered.

## Fences

Tenant isolation is absolute: one tenant's allocation, origin and results are never visible or usable by another. Enrollment is the user's own act under their own connection; no owner credential or owner machine is ever enrolled on another user's behalf. Charging and economics follow HOSTING-COST-POLICY. Backups inherit the established posture (the git worker's encrypted snapshot export pattern; activation optional, not a production gate). Repository CI at the exact head remains the merge gate; Playground verification never replaces it.

## Acceptance

A non-operator machine enrolled by its owner — the owner's PC, instance #1 — runs a real appliance-desk verification through the existing execution surface, with results recovered by handle; the enrollment canary precedes real work; revocation mid-execution terminates the workload; a second tenant cannot see or use the first tenant's allocation. Live acceptance is claimed only from that pass, never from source tests or unit checks.

## Drift check

This card extends PLAY-1's host model; it does not amend PLAY-1's scope, the recorded hosting split (except the fallback question it explicitly opens above), the RTC 2 contract, or any shipped dialect. Where this card and PLAY-1's live corrections conflict, PLAY-1's operational record governs the operator host and this card governs enrolled hosts.

## 2026-10-31 — Phase 1 design and ordered implementation contract

**Status: design recorded before implementation.** This is the commissioned PLAY-2 scope, not a claim that a PC has been enrolled, a tunnel is reachable, appliance-desk has been measured, or a real workload has passed. The original acceptance above remains unchanged. Owner/user enrollment is a separate authority boundary; a builder may make the software and test it with fakes, but cannot enroll an owner's real device or key on someone else's behalf.

**Observable delivery outcome:** A signed-in user enrolls one personally controlled machine and gets one exact tenant-bound, generation-pinned placement for their existing Playground workspace. After an authenticated canary and verified readiness, the unchanged `github_playground_execute/read/cancel` surface performs a real job with durable result handles; a foreign tenant is denied and enrollment revocation terminates that host's work, with independent observable cleanup.

**Proof required:** disposable real-PostgreSQL tenant tests for ownership, replay, migration and denial; signed dispatch and host-key/tunnel tests; actual container/image tests for canary, isolated startup, recovery and revocation; exact-head `ci` and `release-policy` before merge; then owner-operated PC pairing and live appliance-desk verification from the custom MCP. Unit tests and published source are not live acceptance.

### Sequence and placement

1. **Tenancy and authority:** define enrollment and placement persistence, pinned identities and migration from existing operator records; the reader must never cross tenant, connection/pass or workspace scope.
2. **Pairing and canary:** specify the on-device installer, user-confirmed one-time pairing, host key, image/supervisor update contract and pre-work fitness proof.
3. **Transport:** first supported path is a **user-owned outbound HTTPS tunnel** with an origin pinned during authenticated pairing, not a raw tailnet name or agent-chosen URL. The device-initiated relay alternative is deferred until a bounded, supported always-on relay and its costs are designed; Vercel's request/response functions must not be assumed to host indefinite WebSockets.
4. **Capacity, isolation and shutdown:** decide truthful resource claims, user-visible host trust, lease/revocation behavior, stopped-process and volume evidence.
5. **Transfer benchmark:** measure the genuine appliance-desk working directory (not just repository source), choose the attachment path using the recorded limit and fail safely for unsupported state.
6. **Fallback economics:** decide supported subset/payer before any Vercel Sandbox or hosted allocation code.
7. **Build independently useful Phase 2 outcomes,** with source tests and CI for each. PLAY-1's released operator-host acceptance remains a parallel, independent task; PLAY-2 neither waits for it to design nor marks it complete.

This is **PLAY-2**, not PLAY-1 completion and not PUB: PUB owns authenticated per-user identity, PLAY-1 owns the execution contract/operator-host lifecycle, and PLAY-2 adds user-enrolled host trust, reachability, and placement. No new agent-facing tool family or RTC dialect is approved.

### A. Persisted enrollment and allocation shape

Use additive, tenant-owned persistence in the existing PUB-1 schema discipline, not global operator `PLAYGROUND_ALLOCATIONS` rows as the authority for enrolled devices. A device enrollment record must bind the exact tenant/identity, enrolling user's active connection (or explicitly bounded delegated pass), device ID, host Ed25519 public key/fingerprint, owned outbound-tunnel HTTPS origin, origin/TLS pin, capability/image revision, selected capacity policy, monotonic enrollment generation, status (`pending_canary | ready | constrained | recovery | revoked`), and last independently verified heartbeat. Never store a GitHub token, tunnel credential or device private key in this record or present an origin through a tool parameter.

Each allocation remains uniquely bound to tenant + `workspace_id` + existing SHA-256 `playgroundBinding(record)` + original repository/connection authority, with enrollment ID/generation, immutable host/origin pin, observed enforcement and execution/cleanup phase. A root-level sweep index may contain **only** the opaque routing/scope identity needed to locate its tenant; authorization, host pin and data remain in the tenant's namespace. Use CAS revisions, uniqueness and durable tombstones for concurrent enrollment, double-submit, reuse and revoke/re-enroll. One host is available only to its enrolling tenant; even a legitimate device owner never offers this host to another tenant via this flow.

Provider-operated allocations remain pinned and continue using existing `ensureAllocation`, `allocationAuthority`, sealed attachment and lifecycle logic. A discriminator such as `placement_kind=operator|enrolled` chooses the backing adapter **after** current-connection authorization. Migration is additive and lazy; do not bulk-copy legacy operator settings to individual users or silently move an active workspace. An unknown kind, stale generation, changed pin or inconsistent tenant/connection fails closed before any request/credential is sent.

### B. Installer, pairing, image updates and readiness canary

The enrolled user starts from **their own authenticated connection** and requests a short-lived, single-use pairing code in the protected connection UI. The on-device WSL2/Docker installer is transparent, reversible and offline-checkable; it verifies a pinned signed release/image digest, installs the existing immutable coding-workspace image and separate supervisor/broker, generates a device-only Ed25519 keypair locally, and pins the control-plane public verification key. The browser approves the exact displayed device fingerprint and tenant under the same current identity; both endpoints prove possession using an expiration-bound, single-use server challenge. A code copied to another tenant, old grant, wrong device key, replayed challenge or revoked user must fail. The bench GitHub key is never uploaded, copied to the command container or used as an implicit service credential.

The device supervisor, not user code, controls the container runtime. It alone holds local Docker privileges and the host signing key. The arbitrary-code container keeps UID 1000, no socket, no private host mount, no provider/tunnel/key secrets, internal-only ingress and the existing scanner and log boundaries. Support an opt-in, signed, immutable image/supervisor update channel with explicit version/capability compatibility, drain of existing receipts before cutover and rollback to the pinned prior version; critical incompatible revisions become `recovery`, not an invisible auto-upgrade of live allocations.

Before `ready`, execute a disposable **enrollment canary**, bound to that exact device, tenant, image and enrollment generation. Reuse the real CODING-WORKSPACES rehearsal: signed command, Node 24, test PostgreSQL start/stop, Playwright Chromium, isolated shared worktree/read-only Git metadata, receipt/log byte-window recovery, denied foreign tenant, no public preview port, runtime cgroup readings where available, current-grant heartbeat and exact disposable stop/volume absence. Capacity measurements must distinguish measured values from configured limits. A failed or incomplete canary never promotes the host. The actual appliance-desk acceptance is a distinct, later test.

### C. NAT transport and 90-second claim semantics

An outbound tunnel **initiated and owned by the device user** exposes only the narrow signed worker/broker HTTPS paths through a fixed origin registered during pairing. Pairing verifies reachability, TLS identity plus host key and the exact origin; rotation/replacement requires a fresh enrolled generation and authenticated user action. Restrict internet ingress with the tunnel's available controls; the worker must still reject unsigned, expired, wrong-purpose, wrong-binding, wrong-host, wrong-tenant or replayed requests. A private tailnet IP/name alone is not a Vercel-routable control-plane origin; the tunnel's provider/account/domain choice is a per-user installation prerequisite and cannot be silently borrowed from the operator's account.

The existing request claim is signed immediately before transport and expires in **at most 90 seconds** (current controller normally signs for 60 seconds). The tunnel is a transport, never an authority to refresh, queue, replay or forward a claim after expiry. On timeout/disconnect: preserve the original requestKey/journal/24-hour handle; query the original receipt on reconnection after fresh service authorization, and never auto-run an uncertain command under a new key. Require clock/skew diagnostics and fail-closed deadline checks. Existing 4-hour **idle** workspace life is separate from the 90-second per-request authority and must not silently become a four-hour bearer grant.

### D. User hardware, isolation and availability

**Default for enrolled personal hardware: best effort, with honest device-advertised capacity;** the user chooses optional lower CPU/RAM/disk policy limits within actual observed capability and the PLAY-1 eight-CPU/eight-GiB/150-GB workspace targets. Do not label available disk, configured cgroups or a claimed driver name as a reserved 150-GB quota. Report measured/enforced/unknown fields separately and expose `ready/constrained/recovery/git_only` through existing availability reads. Protect host responsiveness, keep bounded CPU/memory pressure admission and deny when actual private-network/host/credential separation cannot be confirmed; no paid resources or implicit hosted reroute. The existing owner-approved PLAY-1 best-effort baseline is not a promise of measured guarantees.

**Trust disclosure:** this is **the user's own machine and only their tenant's work**. The host owner can administer and inspect their own filesystem/processes; Docker/WSL2 containers are not hypervisor VMs, and this enrollment does not provide mutually hostile tenant isolation on a shared PC. Never place another tenant's code, data, Git credentials or allocations on it. Explain before pairing that user-controlled workloads can consume local disk/CPU, downloaded code may be untrusted, the machine may sleep or disconnect, local loss is possible, and volume backup is optional. Bind the hosted command container to a dedicated internal network; publish no general-purpose port or host Docker socket.

### E. Revocation, sleep, updates and cleanup evidence

**Revoke = terminate, not drain.** On explicit unenrollment, user/grant revocation or tenant removal, atomically revoke the enrollment generation, stop new dispatch, invalidate every bound allocation, and ask the device supervisor to terminate the entire executor/container namespace and all exact run-owned mounts/volumes. Host rotation/update with a valid grant instead uses **drain without killing** until active receipts are safe, then a checked cutover; old host pins remain recorded until verified empty. A sleeping/offline machine cannot acknowledge remote revocation in real time: its supervisor must fail closed when short-lived current-grant authorization/heartbeat expires, and remote state remains `revocation_pending` until the device reconnects and supplies evidence. An offline API reply alone is not a claim that every local process stopped.

On a machine outside operator inspection, the separately privileged supervisor enumerates actual container/process identities, mounted allocation paths and the exact run-owned volumes before and after deletion. It signs fresh binding/generation/nonce/expiry-bound cleanup observations; the control plane independently requires the observed execution/container namespace and all expected owned resources to be absent, with no foreign resources affected. This is **device-attested evidence**, not an assertion of independently inspecting a potentially malicious owner's physical machine. Report that limitation. Lost acknowledgement causes readback/recovery, not a second blind deletion. Deny stale, wrong-tenant, partial, ambiguous or replayed observations. Do not delete the Git source workspace before safe transfer/readback.

### F. Appliance Desk transfer measurement and selection

**Not yet measured.** A GitHub repository snapshot is not the actual workspace: uncommitted edits, generated files, symlinks, ignored dependencies and broker metadata can change transfer size or eligibility. A benchmark must run inside an authorized disposable **appliance-desk workspace** (owner-supplied current worktree or exact disposable equivalent) before promising device attachment. Record the immutable Git HEAD, native job generation, working tree state, allowlisted file count, total raw bytes, largest file, symlink count/targets (without secrets), ignored/generated data category totals, manifest/hash, elapsed transfer time, and whether the current **100 MiB and no symlinks** sealed-export contract succeeds. Never print private file bodies or keys into the card/log.

**Decision rule:** for a fully permitted snapshot no larger than the existing export contract and no symlinks, prefer the existing generation-bound encrypted sealed transfer and independently verify readback. Otherwise design/use a **device-local direct clone in the privileged native-Git broker** with exact current repository authorization, temporary scoped provider/bench credential held only outside executable code, pinned Git HEAD/remote/known-host identity, and verified full tree/ancestry. Then separately reconcile allowed uncommitted files against the source generation with manifest checks and conflict refusal; a fresh clone alone must **not** discard local edits or be called an attached workspace. Do not simply raise the 100-MiB cap without measured transfer, timeout, memory, storage and secret exposure evidence. Device acceptance is blocked on this measurement/path, not the tenant registry design.

### G. Hosted fallback decision — no fallback implementation in PLAY-2 Phase 1

**Decision: keep the existing operator Dokploy pool as the only candidate for full-size hosted Playground, conditional on explicit capacity and economics; no automatic free pool allocation or paid upgrade is authorized.** If a separately offered hosted tier is later funded, the **operator's** Dokploy/Vercel/Neon accounts and measured quota bear its cost; customers only pay if the owner separately approves and publishes a price/plan. The user's own device, electricity and tunnel account are the user's costs under bring-your-own-compute. Keep the existing Git/GitHub and repository-CI alternative available when no enrolled host or funded hosted slot exists. A non-owner user is never silently run on the owner's PC.

**Vercel Sandbox assessment (checked against Vercel's published 2026 docs):** Hobby limits a continuous session to **45 minutes**, **4 vCPUs/8 GB RAM**, so it cannot honor a single four-hour Playground execution. Pro/Enterprise support **24-hour** continuous sessions and Pro up to **8 vCPUs/16 GB**, so a four-hour Node/PostgreSQL/Chromium workload is technically plausible but not accepted without image, service-lifecycle, isolation, preview and real-workload proof. Published Sandbox ephemeral storage is materially below the requested **150 GB** (current Sandbox guidance describes a 64-GB environment); Vercel Drive is a distinct billable, configured persistent mount that may support larger data, but cannot silently be treated as the existing four-volume/150-GB allocation contract. Snapshots preserve files, **not running PostgreSQL/Chromium processes** after stop; an uninterrupted four-hour command needs Pro or higher. Operator-created sandboxes bill the **operator's Vercel account**, not the customer's; customer-billed BYO Vercel would be an additional credential/provider enrollment product and is not implemented. Hobby is also non-commercial. Existing HOSTING-COST-POLICY disallows a new paid service or expense without owner approval. Therefore do **not** build or advertise Vercel Sandbox as the full free fallback. A separately scoped short-lived, small-storage, opt-in sandbox tier would need its own approved economics and acceptance.

Sources checked 2026-10-31: https://vercel.com/sandbox ; https://vercel.com/kb/guide/vercel-sandbox-duration-and-persistence ; https://vercel.com/pricing ; https://vercel.com/changelog/vercel-drives-is-now-generally-available . Distinguish product limits from a claim that any billing or subscription setting was changed (none was).

### H. Additional risks, independent prerequisite and Phase 2 slices

- **New live blocker beyond the original card:** a tailnet-only machine is not reachable from the public Vercel control plane. First-device pairing needs a user-owned stable outbound HTTPS tunnel/hostname with verified end-to-end pinning, DNS/rebinding prevention and a trusted claim path; do not substitute a local IP or request a hostname in an agent tool. WSL2/Docker availability, local network policy, sleep/clock behavior and ownership confirmation must be observed on that machine before PC acceptance.
- **Fail-closed offline revocation is a real limit:** no server can remotely prove instantaneous termination of a powered-off/disconnected host. Require bounded local lease expiry, later attestation and an explicit pending state rather than a false success.
- **Image/key supply chain:** immutable image+supervisor signing, update-key custody, package installation origin and rollback matter because the supervisor will control the user's Docker host. A registered bench GitHub key does not confer control-plane consent or permit credential sharing.
- **Source transfer:** real appliance-desk dirty-worktree measurement and user consent are required before a pass; GitHub source size alone is insufficient. The owner/operator's separate Dokploy network-address-pool exhaustion is a PLAY-1 infrastructure issue, not a reason to block enrolled PC design or to consume other tenants' subnets.

Suggested coherent implementation outcomes (same card, append dated results as each lands): **(1)** tenant enrollment/placement data, pairing UI and real-database denial tests; **(2)** signed installer/supervisor, outbound tunnel pinning, canary and image CI; **(3)** adapter integration through existing execute/read/cancel, attachment benchmark/direct-clone when needed, offline/revoke/cleanup and real end-to-end PC acceptance. Split only across actual review/safety boundaries, not by individual helpers. Each PR has its own acceptance, tests, exact-head CI and source/merge/release/live evidence. PLAY-1's operator-host live acceptance proceeds independently alongside these units.

**Phase 1 evidence and unresolved gate:** card and index changes are design only. No bench workspace was accessed, no device installed/paired, no tunnel credential obtained, no provider paid, and no real machine command dispatched. Phase 2 code can start on synthetic owned fixtures; owner-PC acceptance waits for user-initiated pairing, supported outbound tunnel and true appliance-desk worktree measurement.
