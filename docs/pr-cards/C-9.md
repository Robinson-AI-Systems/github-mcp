**Approved:** owner request 2026-10-27: close the reproducible same-file custom versus official MCP latency gap without buying compute, removing capabilities, or weakening any access boundary. **State:** implementation branch prepared; exact-head CI and real production latency still pending. ## Whole-outcome acceptance

1. **One fresh proof per request.** Every tenant MCP request independently verifies signed token, live active membership/pilot, marketplace state, exact tenant schema, client existence, bearer hash/expiry/revocation and every authorized account. Reuse the same in-request membership and marketplace evidence for the tenant-opening phase instead of querying them again. No cross-request caches, foreign schema, stale authorization, or user-controlled bypass.
2. **Bounded parallel hot path.** Perform independent directory reads concurrently and account/client existence reads concurrently (at most ten accounts); preserve failure-closed behavior, exact account and app/production checks, and original response semantics. Avoid introducing unbounded PostgreSQL fan-out.
3. **Regression and measurement.** Test success, revoked pilot/client, inactive marketplace, wrong namespace and absent/foreign accounts, including artificial-delay concurrency tests. Record a reproducible before/after synthetic latency budget. Preserve real SQL tenant isolation, existing auth and quota tests and ensure no GitHub write side effect.
4. **Finish.** Run the available source checks and focused tests, all exact-head required CI jobs, review the auth diff and resolve findings, merge only if green. Deployment stays on the scheduled checked `live` promotion unless owner separately authorizes a one-off release. Compare live real-tool samples only once that exact commit is deployed.

## Boundaries

No new credentials, cached bearer validation across HTTP requests, capacity-price increase, production permission change, weakened marketplace or pilot revocation, direct commit to main/live, or altered GitHub capability gates.
