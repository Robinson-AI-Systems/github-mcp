# Native Git capacity for parallel agents

Owner asks to scale native Git for multiple active AI agents. Plan before configuration/test changes: validate four independent simultaneous workspace requests, retain one request per workspace and bounded overload, then change only the existing Render concurrency setting from two to four. No compute/disk/instance increase or new paid service. The API-based GitHub tools already operate concurrently; this cap applies only to the native execution plane.

Baseline: authenticated capabilities reports two. Render provider samples over the preceding hour show maximum memory about 41 MiB against 512 MiB and maximum sampled CPU about 0.052 CPU against 0.5 CPU. These are sampled observations, not transient peaks or a large-clone load guarantee. Current persistent-disk constraints retain a single process/instance; adding replicas would not share its disk safely.

Acceptance: a deterministic signed HTTP test admits four independent requests at once, refuses same-workspace overlap and an extra request, then releases capacity correctly. On the already checked worker code, set four through the existing environment API, verify unchanged source/plan/disk and signed readiness, create four exact disposable scratch workspaces, submit parallel distinct writes to one relative filename, verify exact isolated bytes and complete cleanup. Observe provider resources after the probe; revert to two if service errors or resource pressure appear. Keep the Blueprint and operating guide consistent with the selected setting through normal checked PR merge. No claim that any number of agents or arbitrarily large clones fit this host.

## Actual deployed result

The existing worker remains on checked source `0d75243923fd2e2eb7928bf2aafbf4f9b4a00867`; no executable runtime change or MCP application release was needed. Only NATIVE_GIT_MAX_CONCURRENT was merged into the existing service environment at 4. Render independently reports the resulting deployment live on that same commit. Signed custom MCP capabilities confirms ready=true/protocol2/Git2.39.5/max_concurrent4. Same single instance, 0.5c-512mb plan, 1 GB disk, persistent root, public verifier and manual source deployment policy. The approximately $7.25/month starting compute/storage estimate is unchanged; this is not a guarantee against ordinary usage overages.

Authenticated actual custom MCP acceptance used one exact run-created private scratch repository (3468). Four parallel workspace-open calls all applied and independently confirmed, generation0 (3470–3473). Four parallel write_file calls wrote distinct harmless contents to the same agent.txt path (3475–3478), each confirmed at generation1. Independent parallel byte reads returned exactly A/newline, B/newline, C/newline and D/newline in their respective workspaces, with four distinct SHA-256 hashes. No read/write retries or workspace mixing were needed. This proves the tested small-repository workflow, not throughput for arbitrary repository sizes.

All four exact workspaces disposed and independently confirmed (3480–3483); exact repository deleted and confirmed (3484). Separate primary GitHub GET returned 404; accessible workspace inventory no longer included any of these fixture IDs. No unrelated workspace or repository was deleted.

Provider samples for the replacement worker through 06:19 UTC showed approximately 39 MiB memory and 0.038 CPU against the unchanged 512 MiB/0.5 CPU allocation. One-minute samples may miss short peaks and include other legitimate traffic. They do not prove large-clone capacity or isolate this probe's individual resource cost. No service error or measured pressure required rollback during this probe.

Local real-Git signed service suite: 13 tests passed, including deterministic held-request admission at both two and four, same-workspace409, capacity429/Retry-After and successful reuse after release. The repo Blueprint and current owner/operations guides now select four. Required exact-head checks/review and merge are tracked on the associated configuration PR; no additional runtime deployment is needed merely to publish this evidence.

## Next capacity decision

This request is satisfied at four simultaneous native workspace requests on the current host; more agents may retain separate workspaces and interleave short operations. The API-based GitHub tools are outside this native limit. If observed native contention, CPU saturation, memory pressure or disk growth makes this insufficient, measure a representative workload and propose a specific compute/storage cost before any paid enlargement. Keep each workspace serialized and retain generation/ref checks. A multi-worker fleet needs explicit workspace routing plus independent durable storage per worker or a designed shared-state architecture; do not attach replicas to one Render disk or imply that raising a number builds autoscaling.
