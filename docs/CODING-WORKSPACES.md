# Robinson's Playground — integrated coding workspaces

Robinson's Playground is Robinson AI Systems' runtime/sandbox for the GitHub coding workspace. The owner confirmed GitHub integration first: opening an eligible coding workspace should also make its isolated Playground available for dependency installation, building, running, testing and previews. The150GB storage ceiling remains requested; use grows as needed. This is one workspace experience with one total resource allowance. Google Workspace/Gmail/Drive integration is not part of this first implementation.

## Current status

The live connector still provides native Git workspaces. The new workers/coding-workspace execution image is a source implementation under verification, not a deployed full coding product. It is intentionally not registered as an agent-facing tool until authenticated provisioning, Git synchronization, revocation, preview access and whole-workspace cleanup are integrated. Never enable shell execution inside the existing shared native Git worker.

A workspace is the agent's complete working environment; its runtime is the software executing commands inside it. The requested eight virtual CPUs, eight GiB RAM and150GB disk cover the WHOLE workspace. Builds, tests, browser, development server, test database and supervisor share these ceilings; they do not each receive another allocation. CPU means an execution ceiling, not eight dedicated physical cores. Memory-backed temporary files also count against the same memory ceiling. Disk storage is allocated as used; a maximum is not a reserved150GB SSD purchase.

## Execution image contract

Each instance has one immutable authenticated binding and one separately provisioned persistent volume. The HTTP supervisor runs as the isolated container root; commands run UID/GID1000, with no inherited host environment or provider/orchestrator credentials. Private root-owned receipts/logs cannot be rewritten by commands. The image contains Node, npm, Python, Git, native build tools, PostgreSQL15 and a pinned Playwright Chromium. Commands use explicit argv; a user can deliberately invoke a shell. They can install dependencies in the writable workspace, run build/test scripts, keep a development server running as an asynchronous execution, and start the credential-free disposable test database using /bin/sh /app/workers/coding-workspace/test-database. DATABASE_URL points only to that workspace's loopback test cluster; never put a production URL in the image.

POST /v1/coding accepts purpose-separated, binding-pinned Ed25519 claims valid for at most90seconds. The control plane must freshly authorize the real connection/repository and explicitly selected execution permission before signing any request. It must not put a GitHub token in these claims or in the container. Provider authentication remains outside arbitrary-code processes. Only a public verification key belongs here. The standalone endpoint does not by itself implement a provider authorization, revocation or tenant-enrollment service.

Actions are capabilities, start, status, logs and cancel. start takes a stable requestKey, argv, optional repository-relative cwd and a finite timeout up to four hours. It durably reserves an intent before spawning; a different command with the same key is refused. Restarted incomplete receipts become uncertain and never silently rerun. Commands return asynchronously, retain actual exit/signal state and expose all retained redacted output in hash-pinned byte windows (pass the previous logHash as expectedLogHash when continuing). Changing output requires restarting the read or waiting for completion, preventing silent gaps. Exceeding the explicit32MiB per-execution log bound terminates the command as failed; it is not silently truncated success. Logs and repository output remain untrusted. Scanner limitations still apply.

Cancellation terminates the command's original process group. A malicious process can create a different session; final workspace termination MUST stop the entire container/PID namespace. Do not promise that a process-group signal proves removal of every daemonized descendant. Four hours without an authorized command/status/log/cancel interaction stops active groups and closes the supervisor. Health/capabilities do not extend the lease, and background process output is not agent activity. External lifecycle reconciliation must still stop the entire allocation and remove its exact volume after authorized disposal/expiry; Docker volumes do not disappear when a process exits.

## Mandatory provisioning integration before exposure

1. Provision a separate allocation for every authenticated workspace. Enforce and independently read back8CPU/8GiB and a real150GB storage quota, including writable application data, caches, test database and execution logs. The Compose sample deliberately requires an externally provisioned volume; it does not invent a named-volume quota. Include image/container scratch usage in host admission. No Docker socket, privileged mode, host PID namespace or host filesystem mount is permitted in the coding container.
2. Keep the private workspace network isolated from other tenants, host administration and production databases. The operator must provide an egress arrangement that permits dependency/browser downloads without exposing private host services or other tenant networks. An external network name alone does not prove this. Default shared dokploy-network membership is insufficient. No public unauthenticated development ports.
3. Add project-scoped provisioning and a trusted registry outside the coding container, binding tenant, connection/pass, repository, job, allocation origin, volume and current lease. Real resource pressure governs admission; no daily quota or arbitrary workspace-count allowance. Keep signed origins operator-configured; never accept a caller-supplied credential destination.
4. Use a separate trusted Git broker plus reviewed file/snapshot synchronization with full manifests, current generation/head checks and explicit exclusions/size bounds. Never share a provider token, another workspace's volume or writable control receipts with executable repository code. Preserve uncommitted edits in both environments; conflict/partial transfer cannot be labeled success. Existing native workspaces keep their host pins and data until explicitly migrated.
5. Add the compact MCP execution/read surface through the existing search/describe/call registry. Reuse journal/replay, actual connection/pass restrictions, fresh repository authorization, redaction/complete result retrieval and revocation. Recheck permission on every interaction; revocation also requires authenticated termination of previously started workloads. Implement authenticated preview proxy/browser access and exact allocation/volume cleanup. Do not claim these integrations are already delivered by the standalone supervisor.
6. Rehearse on disposable allocations: real dependency installation, application TypeScript/Next.js build, tests, database migrations, Playwright, authenticated development preview, cross-tenant denial, revoked grant, idle renewal/expiry, quota exhaustion, restart/replay, independent pushed-head verification and exact cleanup. Measure the same application/revision/test workload against the comparison VM before making performance claims.

## Current infrastructure evidence

The project deployment can be inspected through Dokploy. Server health and available-server inventory were denied401 for docker/member resources; backing-volume quota enforcement remains unverified. Request project-scoped observations/provisioning support from the operator, rather than host-wide permissions or credentials in chat. Existing Render/Dokploy jobs and both volumes remain untouched. The current image's capacity response reports actual cgroup quota/usage, scheduler parallelism, available process memory and filesystem availability where observable. Unknown measurements stay null. Filesystem free space is explicitly NOT a per-workspace quota or an SSD reservation.

## Verification route

The unit suite tests real Ed25519 purpose/binding/expiry checks and capacity interpretation. The separate Coding workspace image workflow builds the pinned image, then runs real UID separation, durable replay, restart uncertainty, HTTP dispatch, timeout/cancel, complete log windows, resource admission, inactivity, npm lifecycle installation, TypeScript execution, application tests, PostgreSQL and Playwright tests with no network or provider credentials. This offline fixture is not a real Appliance Desk build, a host deployment, VM-grade hypervisor isolation or a performance benchmark. Containers share the host kernel; a hostile-code multi-user deployment also needs an operator-approved sandbox/runtime isolation decision.
