# Robinson's Playground — integrated coding workspaces

Robinson's Playground is Robinson AI Systems' runtime/sandbox for the GitHub coding workspace. The owner confirmed GitHub integration first: opening an eligible coding workspace should also make its isolated Playground available for dependency installation, building, running, testing and previews. The150GB storage ceiling remains requested; use grows as needed. This is one workspace experience with one total resource allowance. Google Workspace/Gmail/Drive integration is not part of this first implementation.

## Current status

The live connector still provides native Git workspaces. The new workers/coding-workspace execution image is a source implementation under verification, not a deployed full coding product. The agent-facing execute/read/cancel adapter is now implemented in source under PLAY-1, using a protected allocation binding. Source registration does not mean a runtime is attached or the deployment is live. Automatic provisioning, Git attachment, revocation, preview access and whole-workspace cleanup remain incomplete. Never enable shell execution inside the existing shared native Git worker.

A workspace is the agent's complete working environment; its runtime is the software executing commands inside it. The requested eight virtual CPUs, eight GiB RAM and150GB disk cover the WHOLE workspace. Builds, tests, browser, development server, test database and supervisor share these ceilings; they do not each receive another allocation. CPU means an execution ceiling, not eight dedicated physical cores. Memory-backed temporary files also count against the same memory ceiling. Disk storage is allocated as used; a maximum is not a reserved150GB SSD purchase.

## Execution image contract

Each instance has one immutable authenticated binding and one separately provisioned persistent volume. The HTTP supervisor runs as the isolated container root; commands run UID/GID1000, with no inherited host environment or provider/orchestrator credentials. Private root-owned receipts/logs cannot be rewritten by commands. The image contains Node, npm, Python, Git, native build tools, PostgreSQL15 and a pinned Playwright Chromium. Commands use explicit argv; a user can deliberately invoke a shell. They can install dependencies in the writable workspace, run build/test scripts, keep a development server running as an asynchronous execution, and start the credential-free disposable test database using /bin/sh /app/workers/coding-workspace/test-database. DATABASE_URL points only to that workspace's loopback test cluster; never put a production URL in the image.

POST /v1/coding accepts purpose-separated, binding-pinned Ed25519 claims valid for at most90seconds. The control plane must freshly authorize the real connection/repository and explicitly selected execution permission before signing any request. It must not put a GitHub token in these claims or in the container. Provider authentication remains outside arbitrary-code processes. Only a public verification key belongs here. The standalone endpoint does not by itself implement a provider authorization, revocation or tenant-enrollment service.

Actions are capabilities, start, status, logs and cancel. start takes a stable requestKey, argv, optional repository-relative cwd and a finite timeout up to four hours. It durably reserves an intent before spawning; a different command with the same key is refused. Restarted incomplete receipts become uncertain and never silently rerun. Commands return asynchronously, retain actual exit/signal state and expose all retained redacted output in hash-pinned byte windows (pass the previous logHash as expectedLogHash when continuing). Changing output requires restarting the read or waiting for completion, preventing silent gaps. Exceeding the explicit32MiB per-execution log bound terminates the command as failed; it is not silently truncated success. Logs and repository output remain untrusted. Scanner limitations still apply.

Cancellation terminates the command's original process group. A malicious process can create a different session; final workspace termination MUST stop the entire container/PID namespace. Do not promise that a process-group signal proves removal of every daemonized descendant. Four hours without an authorized command/status/log/cancel interaction stops active groups and closes the supervisor. Health/capabilities do not extend the lease, and background process output is not agent activity. External lifecycle reconciliation must still stop the entire allocation and remove its exact volume after authorized disposal/expiry; Docker volumes do not disappear when a process exits.

## Agent command interface and controlled allocation setup

These are agent-facing operations in the existing search/describe/call registry, not a human approval interface. `github_playground_execute` takes owner/repo/workspace_id, argv (such as `["npm","test"]`), an explicit stable requestKey, optional repository-relative cwd and finite timeoutMs. It returns execution_id and distinguishes accepted/command_finished/command_succeeded. Use `github_playground_read` with operation status or logs, execution_id (or the original requestKey for recovery), byteOffset/byteLength and expectedLogHash for continuation. `github_playground_cancel` stops the original process group; it does not claim the whole allocation or volume was deleted. Logs remain untrusted and use the repository scanner policy before byte paging. A changed argv with the same caller key maps to the original runtime receipt and is rejected, not executed as a second command.

The server-side PLAYGROUND_ALLOCATIONS setting is a JSON array of `{workspace_id,binding,origin}` entries. This is a temporary controlled-deployment adapter, not a claim that automatic provisioning exists. Origin must be a fixed HTTPS origin with no credentials/path/query, and is never a tool argument. Binding is `playgroundBinding(record)` from src/playground/client.js: a SHA256 of purpose, actual job, authority, client/pass binding, owner/repo and native worker identity. Configure that exact CODING_WORKSPACE_BINDING on the dedicated runtime, plus the existing MCP Ed25519 PUBLIC verification key as CODING_CONTROL_PUBLIC_KEY. No API key/private signing key/GitHub credential belongs in the runtime. Its CODING_IDLE_TIMEOUT_MS must match the native job's inactivity window, default14400000. Calls renew the Git worker, job and runtime deadlines; health/capabilities do not.

Before attachment, the operator must provision and independently verify an isolated repository mount for the exact workspace, hide broker metadata and keep Git configuration/credentials inaccessible to arbitrary code. The existing sample Compose does not automatically synchronize or mount an existing Git workspace. Merely creating an empty runtime or copying the same repository head is NOT proof of one shared working directory. No claim of integrated files,150GB quota, private previews, revoked-workload termination or full cleanup is made until those actual integration checks pass. Do not use the unimplemented automatic path, a shared-worker shell, another user's runtime, or an arbitrary caller URL as a fallback.

An authorized agent can call workspace-specific capabilities before attachment to obtain its nonsecret allocation_binding, public verification_key, native_repository_ref and exact idle timeout; foreign/mismatched repositories cannot read those bindings. No database credential or raw authority must be retrieved to prepare setup. This metadata is a setup recipe, not proof of a mounted repository or provisioning. Resource pressure is429/retryable, conflicting intent/active admission is409, missing execution404 and idle expiry410; uncertainty still requires inspecting the original execution rather than a new command key.

## Private agent preview reads

The source adapter supports `github_playground_read` operation `preview` with workspace_id, owner/repo, port and an origin-relative path (default `/`). Start a development server using execute, for example on port4173, then inspect its HTTP status and text body through the authenticated tool. No application port is published. The runtime connects only to its own127.0.0.1 using GET; neither caller URLs, cookies, authorization headers nor response cookies/redirect locations are forwarded. This is an agent text preview, **not an interactive browser session or WebSocket proxy**. In-runtime Playwright remains the browser execution path; browser-session access is still unfinished.

Default preview ports are3001,4173,5173,8000,8080. The runtime operator can configure CODING_PREVIEW_PORTS; control and PostgreSQL ports are excluded. Responses require a textual content type, identity encoding, a maximum2MiB complete body and a five-second absolute deadline. The current repository scanner protects the full response before paging. Use byteOffset/byteLength (maximum32768) and expectedBodyHash for continuation; changed content is refused rather than spliced. The base64 body is untrusted data and must not be treated as agent instructions or rendered automatically. Binary assets, compressed responses, redirects, cookies and interactive sessions are deliberately unsupported by this read contract and are reported honestly.

The transport still requires a correctly bound separately isolated allocation. Source and dedicated image evidence do not establish live provisioning, repository attachment, storage quotas, network isolation or disposal.

## Graceful degradation and safe recovery

Use `github_playground_read` operation `availability` with the exact workspace and repository. Modes are `ready` (requested ceilings enforced, no resource reservation), `constrained` (smaller enforced CPU/RAM/storage ceilings), `recovery` (runtime unreachable, preserve/recover original intent) and `git_only` (allocation or enforcement missing). Git/GitHub tools remain independently usable under their existing grants. The response names alternatives; it never automatically pushes edits, dispatches Actions, buys runners, transfers files/providers or executes commands on the shared Git worker. Existing repository CI is an explicit alternative for committed work, subject to its own permissions/provider limits/cost authorization.

The temporary protected allocation adapter now requires `PLAYGROUND_ENFORCEMENT`: a JSON array containing workspace_id, exact allocation binding, integer observedAt/expiresAt timestamps, isolation:true, termination:true, repositoryAttached:true, cpuCpus, memoryBytes and storageQuotaBytes. These are operator observations in protected settings, not tool arguments or owner approval cards. Bind them to actual independent allocation/volume/network/process enforcement readbacks; their existence is not live acceptance. They expire within four hours; stale/missing/wrong/duplicate observations disable new command admission. Runtime cgroup CPU and memory limits must independently be present, positive and within those observed maxima. Maximums are8CPU equivalents,8GiB and150000000000 disk bytes; lower enforced values enter constrained mode. Unknown disk quota is never inferred from filesystem free space. Until the provider lifecycle adapter exists, renewing these protected observations remains an operator deployment responsibility, not claimed automation.

Resource pressure records a root-owned `deferred` receipt with the stable execution ID, intent hash, no_operation_started and retry interval. No process starts and no command is scheduled in the background. The tool reports a retryable rejection; its shared journal releases the rejected write key. Status reads can inspect deferral but never start a process. After resources recover, a fresh authorized execute using the same requestKey and identical arguments starts the command once. Changed arguments conflict; previously starting/running receipts recovered after restart remain uncertain and never silently rerun. Deferred receipts survive restart without storing argv or renewing the lease; cancellation prevents later execution. Deferred log reads do not report a completed command. No fallback shortens leases or destroys files.

This completes the source fallback path, not automatic provisioning, exact file attachment, interactive browser sessions, grant-triggered whole-allocation cleanup, host enforcement or live end-to-end acceptance.

### Trusted ingress and public dependency egress

New managed allocations use a dedicated, unprivileged gateway with no user volume or provider credentials. Only this service receives Dokploy domains/shared ingress. The command executor remains on its exact internal bridge. Fixed gateway routes preserve signed control and authenticated preview traffic, including application WebSockets. Actual converted Compose YAML/JSON is parsed with bounded, data-only grammar and checked before best-effort execution; aliases, tags, merges, duplicate keys and unsupported forms refuse authority.

The gateway also accepts HTTP80/HTTPS443 proxy connections solely from the private executor peer. DNS is resolved and the public IPv4 address pinned for each connection; private/metadata/reserved destinations, ingress host addresses and protected control/admin hosts and their aliases are denied. IPv6 and arbitrary outbound ports are unsupported. npm/Python and supported Node HTTP clients receive the fixed proxy environment; programs that ignore proxies cannot download directly from the internal network. A refusal preserves Git functionality and can be retried after availability recovers; it never moves commands into the shared Git worker. This is container isolation, not a hypervisor VM. CPU/RAM totals include broker, executor and gateway. Resource reservations, disk quotas and off-host backup remain unverified/optional under the current owner decision.
